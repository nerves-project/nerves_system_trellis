NSK boot-time research

Can Claude close the loop on Nerves boot time? On a Nerves Starter Kit it built 65 firmware variants and measured 292 boots in a day. Livebook now reaches the IEx prompt in 6.8 s instead of 18.2 s, the mix nerves.new app in 3.9 s instead of 5.9 s, and WiFi gets an address 4 s sooner.

Everything is on one branch: nerves_system_trellis/boot-time-research (compare with main). Start with bench/FINDINGS.md.

Resume boot (hibernation)

Save RAM to disk once, then have the kernel restore it instead of booting: U-Boot banner to a working IEx in 4.63 s (4.36–4.69) against 5.19 s for today's normal boot to the prompt. Most of a resume is the kernel booting far enough to reach the eMMC (~0.85 s) and reading the image (11 MB LZ4, ~1 s).

Not recommended yet: only about half the resumes happened (the kernel sometimes ignores a valid image), a firmware update resumed the old firmware's image, a swap file on /root corrupted it, and USB gadget Ethernet doesn't come back. Details: bench/EXPERIMENTS.md, "Resume boot".

Tried, didn't help

  • Loading drivers before the BEAM (the nerves_uevent idea): drivers load 1.3 s earlier, IEx and WiFi ~0.1 s or less. VintageNet starts configuring wlan0 at ~4.3 s, then scan and DHCP dominate, and early driver loading competes with BEAM startup.
  • nerves_uevent's coldplug: 398 uevents at boot, each its own message and PropertyTable.put. Skipping the scan entirely saves at most ~0.15 s; batching updates is the likely fix. Also found: NervesUEvent.stats/0 recurses forever.
  • Exact boot paths (no failed lookups) and a single-file module bundle: interactive mode with OTP's boot path cache beats both; in embedded mode the cost is preparing code, not finding it.
  • Hardening off (PIE, SSP, RELRO): ≤0.15 s; not worth it.
  • Uncompressed EROFS: +0.2 s. Kernel trim: −16 ms. U-Boot without networking: −28 ms.
  • JIT: not pursued; boot is dominated by code loading.

How the loop works

  1. Build a variant with build-time switches (variant.sh), flash it over ssh, confirm the running firmware UUID.
  2. Reboot over the serial console; timestamp U-Boot, kernel and IEx on the host.
  3. Pull a report from the board: boot-script marks, CPU accounting, dmesg, network events, the module set at IEx.
  4. Five boots, medians, a bootchart; log it in EXPERIMENTS.md; keep only clear wins.

A functional check (all apps started, RingLogger alive) runs every boot, after a crashing app start once looked like a speedup.
